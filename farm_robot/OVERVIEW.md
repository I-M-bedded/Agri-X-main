# 농장 급수 로봇 — 전체 설명서

**이 코드를 처음 보는 사람을 위한 문서입니다.**
실제 설치·운용 절차는 `README.md` 를 보세요. 이 문서는 "이게 뭐고 어떻게
돌아가는가"를 설명합니다.

---

## 1. 한 문장으로

> 밭고랑 **입구에만** 세워둔 ArUco 마커로 고랑을 찾아 정렬한 뒤,
> 고랑 안에서는 **비전(흙 중앙선) + 1D ToF(좌우 벽)** 로 스스로 중심을
> 따라 왕복하며 물을 뿌리고, 물이 떨어지거나 마지막 고랑을 마치면
> **집으로 돌아오는** 라즈베리파이 로봇.

---

## 2. 로봇이 하는 일 (동작 시나리오)

```
   ┌── 밭 ────────────────────────────────────────────┐
   │                                                   │
   │   1번 고랑      2번 고랑      3번 고랑(마지막)      │
   │   ┌──────┐     ┌──────┐     ┌──────┐            │
   │   │      │     │      │     │      │            │
   │   │  ↑↓  │     │  ↑↓  │     │  ↑↓  │            │
   │   │      │     │      │     │      │            │
   │   └──┬───┘     └──┬───┘     └──┬───┘            │
   │    ●1           ●2           ●3 +249(END)         │
   │══════════════════════════════════════════════════│ ← 헤드랜드(통로)
   │  ▲HOME                                            │
   └───────────────────────────────────────────────────┘
```

1. **HOME(1번 고랑 입구)에서 시작**한다.
2. 팻말 `1` 을 보고 입구에 **정렬**한다.
3. 고랑에 **진입하면서 펌프 ON**. 비전 + ToF 로 중심선을 따라 달린다.
4. **비전 + ToF 로 고랑 끝을 스스로 감지**하면 180도 유턴.
5. 물을 뿌리며 **입구로 되돌아온다**. (왕복 모두 살수)
6. 고랑을 빠져나오며 **펌프 OFF**.
7. **헤드랜드로 옆 칸 이동** → 2번 고랑에서 3~6 반복.
8. `249`(END) 마커가 붙은 고랑까지 마치면 **HOME 으로 복귀**.
9. 도중에 **물이 떨어지면 즉시 유턴**해서 HOME 으로 복귀.

**왜 ㄹ자가 아니라 왕복인가?**
ㄹ자로 돌면 마지막에 밭 반대편 끝에 도착해 집까지 오는 경로가 길고 복잡해진다.
고랑마다 왕복하면 항상 헤드랜드(입구 쪽 통로)로 돌아오므로, 집으로 가는
길이 언제나 "옆으로 N칸"이라는 단순한 문제가 된다.

## 3. 왜 마커를 입구에만 두는가 ★

```
   입구 팻말 ●
               ╲
                ╲  ← 여기서부터는 로봇이 스스로 본다
                 ╲    (비전 + ToF 로 중심선 추종)
                  ╲
                   (출구에는 아무것도 없음)
```

### 두 극단 사이의 절충

**마커를 양 끝에 다 깔면** — 로봇은 편해지지만 밭 전체에 인공 표식을
설치해야 합니다. 자율주행이라기보다 레일 위를 달리는 것에 가깝습니다.

**마커를 아예 안 쓰면** — 순수 비전으로 "저기가 3번 고랑 입구다"를
판단해야 합니다. 학습 데이터와 모델 규모가 크게 늘어납니다.

**그래서 가장 어려운 문제(입구 식별)만 마커로 풀고, 나머지는 로봇이
스스로 합니다.**

| 문제 | 해결 방법 |
|---|---|
| 몇 번 고랑인가 | 마커 ID |
| 입구가 **어느 방향**인가 | 마커 방위 |
| **고랑 중심이 어디인가** | **비전** |
| **고랑이 끝났는가** | **ToF + 비전** |
| 집이 어디인가 / 임무가 끝났는가 | HOME·END 마커 |

### 마커는 중심선을 알려주지 못한다 ★

이게 설계의 핵심 제약입니다.

> 마커는 "여기 고랑 입구가 있다"만 말해줍니다.
> 중심선이 마커에서 왼쪽 30cm 인지 오른쪽 50cm 인지는
> **마커 안에 담긴 정보가 아닙니다.**

그 값을 상수로 미리 넣어두면(예: `팻말은 항상 중심에서 오른쪽 30cm`),
현장에서 팻말을 조금만 옮겨 박아도 로봇이 그만큼 빗나가 **이랑으로
돌진합니다.** 그런 사전 지식은 쓰지 않습니다.

**중심선은 비전이 고랑 자체를 보고 직접 찾습니다.**

### 입구 정렬 3단계

```
1단계  마커 방위로 거친 접근
       비전이 아직 고랑을 못 볼 때. 마커를 향해 순수추종으로 다가간다.
       마커 코앞까지 왔는데도 비전이 안 되면 -> ToF 탐침으로 전환

2단계  비전으로 중심 정렬          ← 여기서 중심선이 정해진다
       고랑이 화면에 들어오면 비전의 중앙선 오차로 조향.
       옆으로 이동해야 하므로 호를 그리며 전진해 수렴시킨다.

2.5단계  중심을 유지한 채 입구까지 전진
       여기서 멈추면 고랑 밖에서 정렬이 끝나 펌프가 헤드랜드에서 켜진다.

3단계  진입각만 제자리 회전으로 정밀 조정
       제자리 회전은 위치를 바꾸지 않으므로 방금 맞춘 중심이 흐트러지지 않는다.
```

**진입각은 마커 자세(yaw)로 재지 않습니다.** 작은 평면 사각형은 포즈
모호성 때문에 프레임마다 수십 도씩 튑니다. 대신 `_field_heading`
(헤드랜드에서 90도 선회한 방위, 고랑을 빠져나올 때마다 실제 헤딩으로
재보정)을 씁니다.

### 비전이 고랑을 못 볼 때 — ToF 탐침(probing) ★

비전만 믿으면 흐린 날이나 비 온 뒤처럼 흙 색이 달라지는 날 로봇이
**아예 고랑에 못 들어갑니다.** 임무 전체가 멈추는 셈이라 실용상
치명적입니다. 그래서 ToF 대체 경로를 둡니다.

```
고랑 입구에 코를 조금씩 들이민다 (정렬 속도의 50%)

  양쪽 다 벽 보임          → 고랑 안이다
                            좌우 거리차가 40mm 이내면 중심 → 진입
  한쪽만, 80mm 이내        → 이랑에 붙었다. 반대쪽으로 조향
  한쪽만, 그보다 멀리      → 보이는 쪽에서 멀어지며 전진
  양쪽 다 안 보임          → 아직 고랑 앞. 곧게 전진
  0.8m 갔는데도 벽 없음    → 고랑이 아니다. SAFE_HALT
```

**중심을 사전 지식 없이 '벽 대칭'으로 직접 찾습니다.** 비전이 하는 일과
같지만 근거가 다릅니다(색상 vs 거리). 그래서 조명이 나빠도 동작합니다.

> **탐침 전에 밭 안쪽으로 자세를 먼저 잡습니다.**
> 안 그러면 마커를 향하던 헤딩 그대로 직진해서 팻말 쪽으로 밀려납니다.
> 실제로 고랑 중심에서 28cm 벗어나는 것을 시뮬레이션으로 재현했습니다.
> 탐침은 "곧게 들어가서 좌우를 더듬는" 동작이라 방향이 먼저입니다.

**궤도(무한궤도)에 특히 유리합니다.** 탐침은 각도를 쓰지 않고 좌우
거리차만 봅니다. 궤도는 회전 시 미끄러져 엔코더 각도가 부정확한데,
그 영향을 받지 않습니다.

**검증** — `SimVision` 을 신뢰도 0 으로 실명시켜 흐린 날을 재현했습니다.

| 조건 | 결과 |
|---|---|
| 정상 (비전 살아있음) | 3/3 완주 |
| **비전 완전 실명 + ToF 탐침** | **3/3 완주** |
| 비전 실명 + 탐침 OFF | SAFE_HALT (의도된 동작) |

탐침마저 실패하면 `ENTRANCE_ALLOW_BLIND_CREEP = False`(기본)에 따라
`SAFE_HALT` 합니다. `True` 로 두면 마커 방위만 믿고 들어가지만
이랑을 밟을 수 있어 권하지 않습니다.

### 검증: 팻말을 어디에 박아도 되는가

제어 로직이 설치 위치를 모른다는 것을 실제로 확인했습니다.

| 팻말 위치 | 결과 | 정렬 좌우 이탈 |
|---|---|---|
| 오른쪽 30cm | 완주 | 평균 0.5cm, 최대 2.0cm |
| 오른쪽 45cm | 완주 | 평균 0.4cm, 최대 1.5cm |
| **왼쪽** 35cm | 완주 | 평균 0.3cm, 최대 0.7cm |
| 오른쪽 15cm | 완주 | 평균 0.3cm, 최대 0.9cm |

팻말을 고랑이든 이랑이든, 왼쪽이든 오른쪽이든 편한 곳에 세우면 됩니다.

### 고랑 안에서는 어떻게 달리는가

```
1순위  비전 (흙 HSV → 중앙선)      매 프레임 실제 밭을 봄
2순위  ToF ×2 (좌우 벽 대칭)       비전에 25% 섞어 보정
3순위  엔코더 헤딩 유지            둘 다 죽었을 때
```

비전은 흙 무늬를, ToF 는 실제 벽 거리를 보므로 **오류 특성이 서로
다릅니다.** 한쪽이 흔들려도 다른 쪽이 버텨줍니다.

### 고랑 끝은 어떻게 아는가 ★

출구에 마커가 없으니 스스로 알아내야 합니다.

**주 근거 — ToF 양쪽 벽 소실.** 고랑 안에서는 양옆에 흙 벽이 있다가,
고랑을 벗어나면 확 트입니다. 가장 뚜렷한 물리 신호입니다.

오판을 막는 장치가 셋입니다.

1. **양쪽 동시** — 한쪽만 사라지는 건 이랑이 잠깐 유실된 구간
2. **연속 확인** (`TOF_END_CONFIRM_TICKS`, 3틱) — 노이즈 1회로 확정 안 함
3. **최소 주행거리** (`FURROW_END_MIN_TRAVEL_M`, 1.0m) — 입구 근처 오판 방지

**보조 근거 — 비전 신뢰도 급락** (`FURROW_END_REQUIRE_VISION_AGREE`).
고랑 구조가 사라지면 밴드별 무게중심이 흩어져 직선 피팅이 무너집니다.
커버리지가 아니라 **신뢰도**를 보는 게 포인트입니다. 헤드랜드도 흙이라
커버리지는 높게 유지될 수 있으니까요.

**복귀할 때는 더 쉽습니다** — 입구 마커가 정면에 나타납니다.
`RETURN_ENTRANCE_MARKER_DISTANCE_M`(1.5m) 이내면 빠져나온 것으로 봅니다.

### 시뮬레이션 실측 (고랑 8개, 길이 3.00m)

| 항목 | 결과 |
|---|---|
| 입구 정렬 좌우 이탈 | 평균 0.5cm, 최대 2.0cm |
| 진입 시 끝 판정 위치 | 3.03~3.04m (실제 3.00m) |
| 복귀 시 끝 판정 위치 | 입구를 0.44m 지난 지점 |

진입 끝 판정이 3~4cm 늦은 건 연속 확인 3틱 때문입니다. 고랑 끝에
장애물이 있다면 `TOF_END_CONFIRM_TICKS` 를 줄이세요.

## 4. 센서 4종의 역할 분담

| 센서 | 무엇을 보는가 | 성격 | 언제 쓰이는가 |
|---|---|---|---|
| **RGB 카메라 (ArUco)** | 팻말의 흑백 사각 무늬 | 절대·드문드문 | 입구 식별·정렬, 고랑 번호, HOME/END |
| **RGB 카메라 (비전)** | 흙 색상 분포 | 상대·끊김없음 | 고랑 안 좌우 중심 유지 |
| **1D ToF ×2** | 좌우 이랑 벽까지 거리 | 상대 | 중앙 교차검증, 고랑 끝 감지 |
| **엔코더** | 바퀴 회전 수 | 누적 | 위치·각도 추정, 회전 제어 |
| **적외선(TCRT5000)** | 물통 수위 | 이진 | 물 부족 판정 |

### 카메라 하나로 두 가지를 본다

같은 이미지에서 **ArUco 검출**과 **흙 색상 분석**을 각각 수행합니다.
헷갈리기 쉬운데 완전히 다른 일을 합니다.

- **ArUco** : "나는 밭의 3번 고랑 입구에 있다" (내가 **어디**인지)
- **비전** : "지금 고랑 중앙에서 8cm 왼쪽이다" (지금 **얼마나 치우쳤는지**)

도로에 비유하면 ArUco 는 **표지판**, 비전은 **차선**입니다. 표지판은 몇
미터마다 하나씩만 있고, 차선은 끊김 없이 이어지지만 어디쯤인지는 모릅니다.

실측하면 이렇습니다.

| 로봇 위치 | ArUco | 비전 |
|---|---|---|
| 입구 앞 1.5m | 마커 5개 검출 | 신뢰도 **0.00** (흙이 화면의 2%) |
| 고랑 한가운데 | **검출 없음** | 신뢰도 0.80 |
| 중앙에서 8cm 밀림 | **검출 없음** | 오차 +0.533 |

서로를 대체할 수 없습니다.

### 제어원 우선순위

```
1. 비전    (흙 색상 → 중앙선)   ← 주 제어원
2. ToF     (좌우 벽 대칭)       ← 비전에 25% 섞어 보정
3. 엔코더  (헤딩 유지)          ← 둘 다 죽었을 때
```

비전이 살아 있어도 ToF 를 `TOF_ASSIST_WEIGHT`(0.25) 만큼 섞습니다.
두 센서의 오류 특성이 달라 서로를 보완합니다.

## 5. 부호 규약 — 코드를 읽기 전에 반드시

프로젝트 전체가 이 4줄을 따릅니다. 모든 센서 값이 **무차원(−1~+1)** 으로
정규화되어 들어오므로, PID 게인 하나로 제어됩니다.

1. `theta` (헤딩) : **반시계(좌회전)가 양수**
2. `error` (오차) : **양수 = 오른쪽으로 가야 함**
3. `steer` (PID 출력) : **양수 = 오른쪽 조향**
4. 바퀴 믹싱 : `left = base + steer`, `right = base − steer`

현장에서 뭔가 반대로 움직이면 **코드가 아니라** `config.py` 맨 위의
`SIGN_*` 9개를 `+1 ↔ −1` 로 뒤집으세요.

## 6. 파일 구조와 역할

```
farm_robot/
├── main.py                    진입점. FSM 을 만들어 돌리고 종료코드 반환
├── config.py            ★    설정 전부. 현장에서 만지는 유일한 파일
├── logutil.py                 공용 로거 (11개 모듈이 import)
├── selftest.py                자체 점검 150개 항목
│
├── sensors/                   ── 읽는다 ──
│   ├── camera.py                  카메라 1개를 공유. 항상 BGR 반환 보장
│   ├── aruco_detector.py          마커 → 3D 위치 / 입구 정렬각
│   ├── vision_line_detector.py    흙 HSV → 고랑 중앙선 오차
│   ├── tof_sensor.py              VL53L1X ×2 + I2C 주소 재할당
│   ├── odometry.py                엔코더 → x, y, θ 추정
│   └── water_tank_sensor.py       TCRT5000 → 물 부족 (디바운스)
│
├── actuators/                 ── 움직인다 ──
│   ├── motor_driver.py            차동구동 + 데드밴드 보상 + 회전 종료보장
│   └── pump_controller.py         릴레이/MOSFET + 3중 인터록
│
├── control/                   ── 계산한다 ──
│   ├── pid_controller.py          와인드업 방지 PID
│   └── line_follower.py           4개 제어원 융합 → steer
│
├── navigation/                ── 결정한다 ──
│   ├── furrow_manager.py          고랑 번호 관리
│   └── mission_state_machine.py   전체 임무 FSM (핵심)
│
└── tools/
    ├── setup.py                   현장 브링업 도구 (메뉴 4개)
    └── simulation.py              밭·로봇 시뮬레이터 (selftest 용)
```

### 파일별 동작 논리

**`camera.py`** — 카메라를 여는 프로그램은 하나뿐이어야 하므로 ArUco 와
비전이 이 객체 **하나를 공유**합니다. picamera2 → 실패 시 V4L2 순으로
시도합니다. picamera2 의 `format="RGB888"` 이 실제로는 BGR 배열을 주는
함정 때문에, **항상 BGR 을 반환하도록 보장**합니다. (이걸 놓치면 흙의
주황갈색 H≈10 이 파랑 H≈110 으로 뒤집혀 비전 신뢰도가 늘 0 이 됩니다)

**`aruco_detector.py`** — `estimatePoseSingleMarkers()` 는 OpenCV 4.7 에서
제거되어 `solvePnP(IPPE_SQUARE)` 를 씁니다. 진입각은 마커 자세(yaw)로 재지
**않습니다.** 작은 평면 마커의 단독 자세 추정은 포즈 모호성으로 부호가 튀는
것으로 악명 높고, 팻말이 고랑당 1개뿐이라 두 마커의 상대 위치로 각도를 구할
수도 없기 때문입니다. `compute_post_bearing()` 은 **방위와 거리만** 돌려주고,
진입각은 `_field_heading`(밭 안쪽 방위)에서 얻습니다.

**`vision_line_detector.py`** — HSV 로 흙을 마스킹한 뒤 ROI 를 **가로 4개
밴드**로 나눠 각 밴드 무게중심을 구하고 직선을 피팅합니다. 아래 밴드 = 현재
위치, 위 밴드 = 진행 방향이라 횡오프셋과 기울기를 동시에 얻습니다.
신뢰도는 커버리지가 **너무 적어도 너무 많아도 낮아지는 창(window)** 형태
입니다. 화면 전체가 흙이면 무게중심이 로봇 위치와 무관해지니까요.

**`tof_sensor.py`** — VL53L1X 는 공장 출하 주소가 둘 다 `0x29` 라 그냥 붙이면
충돌합니다. **XSHUT 으로 하나씩 켜면서 주소를 재할당**(0x30, 0x31)합니다.
조향용은 EMA 필터값, "벽이 있나 없나" 판정은 **raw 값**을 씁니다. EMA 로
판정하면 임계값에 점근할 뿐 도달하지 못해 고랑 끝 감지가 늦어집니다.

**`odometry.py`** — `d_θ = (d_right − d_left) / WHEEL_BASE`, 중점 적분으로
x, y 갱신. 단일 채널 엔코더라 회전 방향을 모르므로 **모터 드라이버가 지시한
방향**을 받아 부호를 정합니다.

**`water_tank_sensor.py`** — 매 틱 `poll()` 로 디바운스를 진행하고,
`is_water_low()` 는 확정 상태만 반환하는 순수 조회 함수입니다. 이 분리가
중요한 이유는, 디바운스 함수를 고랑당 1회만 호출하면 첫 호출이 항상 False 라
물이 떨어져도 고랑 하나를 빈 펌프로 더 돌기 때문입니다.

**`motor_driver.py`** — `drive(base, steer)` 하나로 부호 규약을 일원화합니다.
**데드밴드 보상**이 핵심인데, DC 기어모터는 듀티 0.18 이하면 아예 안 돌기
때문에 미세 조향 명령 0.05 가 무시되면 영원히 수렴하지 못합니다.
회전은 **부호 교차 판정 + 절대 타임아웃 + 엔코더 stall 감지** 3중으로 종료를
보장합니다.

**`pump_controller.py`** — 3중 방어. ① 고랑 밖(`set_zone(False)`)이면 무조건
OFF ② 물 부족 시 잠금 ③ 최대 연속 가동 워치독. `tick()` 이 매 틱 릴레이
상태를 재확정해 코드 경로 누락으로 상태가 어긋나는 것도 막습니다.

**`line_follower.py`** — 위 4개 제어원을 융합해 `steer` 하나를 냅니다.
비전이 "중앙"이라는데 ToF 는 계속 치우쳤다고 하면 4초 후 경고합니다.
둘 중 하나가 틀렸다는 신호니까요.

**`mission_state_machine.py`** — 임무 전체를 관장하는 유한상태기계.
상태 12개: `INIT`, `SEARCH_AND_ALIGN`, `TRAVEL_INTO_FURROW`, `TURN_AROUND`,
`TRAVEL_BACK_TO_ENTRANCE`, `EXIT_FURROW`, `HEADLAND_TRANSIT`,
`EVALUATE_MISSION`, `HOME_ARRIVED`, `MISSION_COMPLETE`, `SAFE_HALT`, `ERROR`.

## 7. 배선

### 7-1. 전원 계통 (가장 중요)

```
   12V 배터리 (+) ── 퓨즈 15A ── 메인 스위치 ─┬─→ 벅컨버터 12V→5V ─→ 라즈베리파이 (USB-C)
                                              │
                                              ├─→ 모터 드라이버 (12V 직결) ─→ 좌우 모터
                                              │
                                              └─→ LR7843 MOSFET ─→ 워터펌프

   12V 배터리 (−) ──┬─ 벅컨버터 GND
                    ├─ 모터 드라이버 GND
                    ├─ MOSFET GND
                    └─ 라즈베리파이 GND      ← 반드시 한 점에서 별 모양으로
```

**절대 지킬 것**

- 모터·펌프 전원을 **라즈베리파이 5V 핀에서 뽑지 마세요.** 기동 전류로
  전압이 주저앉아 Pi 가 리부팅되거나 SD 카드가 손상됩니다.
- GND 는 배터리 (−) **한 점에서 별 모양**으로. 데이지 체인으로 줄줄이
  연결하면 모터 전류가 흐를 때 GND 전위가 흔들려 GPIO 가 오작동합니다.
- 벅컨버터는 **5A 이상** 권장. Pi 4 는 5V/3A 인데 싸구려 3A 모듈은 피크
  기준이라 실사용에서 전압이 떨어집니다.
- 커패시터: 모터 드라이버 12V 입력단에 **1000µF/25V**, 벅컨버터 입력단에
  **470µF/25V**. 모터 기동 시 전압 강하가 Pi 리부팅의 주범입니다.

### 7-2. 40핀 헤더 (BCM 번호)

핀 1번은 **USB-C 전원 커넥터 쪽 끝**입니다. 기판 뒷면에서 40개 패드 중
**유일하게 사각형인 것**이 1번입니다.

| 물리핀 | BCM | 연결 대상 |
|---|---|---|
| 1 | 3V3 | ToF ×2 VIN, TCRT5000 VCC, 엔코더 VCC |
| 3 | GPIO2 | ToF ×2 **SDA** (공통) |
| 5 | GPIO3 | ToF ×2 **SCL** (공통) |
| 6 | GND | 공통 접지 |
| 11 | GPIO17 | **좌** ToF XSHUT |
| 13 | GPIO27 | **우** ToF XSHUT |
| 15 | GPIO22 | TCRT5000 **OUT** (수위) |
| 16 | GPIO23 | **좌** 엔코더 OUT |
| 18 | GPIO24 | **우** 엔코더 OUT |
| 29 | GPIO5 | 모터 좌 IN1 |
| 31 | GPIO6 | 모터 좌 IN2 |
| 32 | GPIO12 | 모터 좌 PWM (ENA) |
| 33 | GPIO13 | 모터 우 PWM (ENB) |
| 37 | GPIO26 | 펌프 MOSFET 게이트(SIG) |
| 38 | GPIO20 | 모터 우 IN1 |
| 40 | GPIO21 | 모터 우 IN2 |

### 7-3. 1D ToF (VL53L1X ×2)

```
                    ┌─────────────┐
   3V3 (핀1) ───────┤ VIN         │  좌 ToF
   GND (핀6) ───────┤ GND         │
   SDA (핀3) ───────┤ SDA         │  ← 두 센서가 공유
   SCL (핀5) ───────┤ SCL         │  ← 두 센서가 공유
   GPIO17(핀11)─────┤ XSHUT       │  ← 이것만 따로!
                    └─────────────┘
                    ┌─────────────┐
   3V3 ─────────────┤ VIN         │  우 ToF
   GND ─────────────┤ GND         │
   SDA ─────────────┤ SDA         │
   SCL ─────────────┤ SCL         │
   GPIO27(핀13)─────┤ XSHUT       │
                    └─────────────┘
```

- **VIN 은 5V 가 아니라 3.3V.** 저가 GY-53L1 모듈은 3.3V 전용이라 5V 를
  주면 탑니다.
- **풀업 저항 추가하지 마세요.** Pi 의 SDA/SCL 에 이미 1.8kΩ 이 붙어
  있습니다.
- 모듈의 `INT`/`GPIO1` 핀은 **비워두세요.** 코드는 폴링 방식입니다.
- **왜 XSHUT 만 따로인가**: 두 센서 모두 출하 주소가 `0x29` 라 그냥 붙이면
  I2C 충돌로 아무것도 안 됩니다. 코드가 XSHUT 으로 하나씩 켜면서 주소를
  `0x30`, `0x31` 로 재할당합니다.

**확인 방법**
```bash
i2cdetect -y 1
```
- 프로그램 실행 **전** : `0x29` 하나 또는 아무것도 없음 (정상)
- 프로그램 실행 **중** : `0x30`, `0x31` 두 개가 보여야 함
- 계속 `0x29` 하나만 → XSHUT 배선 문제

### 7-4. 적외선 수위 센서 (TCRT5000)

TCRT5000 은 원래 라인 트레이서용 반사형 적외선 모듈이지만, 여기서는
**물통 수위 감지**에 씁니다. 물이 있으면 반사율이 달라지는 것을 이용합니다.

```
                    ┌──────────────┐
   3V3 (핀1) ───────┤ VCC          │  ← 5V 아님!
   GND ─────────────┤ GND          │
   GPIO22(핀15)─────┤ OUT (DO)     │
                    │ A0 (사용안함)│
                    └──────────────┘
                          ↓
                    ┌──────────────┐
                    │  물통 옆면    │  ← 센서를 "물 부족" 판정 높이에 부착
                    │              │
                    │ ~~~~~~~~~~~~ │  ← 이 높이 아래로 떨어지면 복귀
                    └──────────────┘
```

**주의사항**

- **VCC 는 반드시 3.3V.** TCRT5000 모듈은 LM393 비교기 기반이고 출력이
  오픈컬렉터입니다. VCC 에 5V 를 주면 출력 HIGH 도 5V 가 되어 **GPIO 가
  탑니다.** LM393 은 2V 부터 동작하므로 3.3V 로 충분합니다.
- 모듈의 **가변저항(파란 네모)** 으로 감도를 맞춥니다. 물통에 물을 채운
  상태와 뺀 상태에서 LED 가 확실히 바뀌는 지점을 찾으세요.
- 검출 거리가 **1~8mm 로 매우 짧습니다.** 물통 벽에 밀착시켜야 합니다.
  벽이 두껍거나 불투명하면 동작하지 않으니, 투명 물통이거나 센서를 안쪽에
  방수 처리해 넣어야 합니다.
- 물이 출렁여서 값이 튀는 것은 코드가 `WATER_LEVEL_DEBOUNCE_SEC`(1초)
  디바운스로 걸러냅니다.
- 물이 있는데 "부족"으로 뜨면 `config.WATER_LOW_SIGNAL_ACTIVE_HIGH` 를
  `False` 로 뒤집으세요.
- 배선이 빠지면 핀이 뜬 상태가 되어 값이 랜덤으로 읽힙니다. 코드가
  `WATER_SENSOR_PULL="down"` 으로 내부 풀다운을 켜서 안전한 기본값
  (= 물 있음)이 되게 합니다.

### 7-5. 엔코더

```
   3V3 (핀1) ── VCC     ← 5V 아님! (같은 LM393 이유)
   GND ──────── GND
   GPIO23(핀16)─ OUT (좌)
   GPIO24(핀18)─ OUT (우)
```

코드가 내부 풀업을 켜므로 외부 저항은 필요 없습니다.

### 7-6. 워터펌프 (LR7843 MOSFET)

```
   12V (+) ──┬─────────── 펌프 (+)
             │
            ─┴─ 다이오드 SS34 (띠가 12V 쪽)
            ─┬─
             │
             └─────────── 펌프 (−) ── LR7843 드레인
                                       LR7843 소스 ── 배터리 (−)
   GPIO26(핀37) ─────────────────────→ LR7843 SIG(게이트)
   GND ──────────────────────────────→ LR7843 신호 GND
```

- 펌프는 MOSFET 과 **직렬**입니다. 소스·드레인에 12V 와 GND 를 직접
  연결하면 켜지는 순간 배터리가 단락됩니다.
- **플라이백 다이오드 필수.** 펌프는 모터라서 꺼지는 순간 역기전력
  스파이크가 MOSFET 을 뚫습니다.
- **게이트 풀다운 10kΩ** 이 모듈에 있는지 확인하세요. 없으면 직접
  다세요. 부팅되는 30~60초 동안 GPIO 가 뜬 상태라 펌프가 멋대로 돌 수
  있습니다.

### 7-7. 카메라

GPIO 가 아니라 **CSI 리본 커넥터**에 꽂습니다. 검은 걸쇠를 위로 당겨 열고,
**파란 보강 테이프가 이더넷/USB 포트 쪽을 향하게** 넣은 뒤 걸쇠를 누르세요.
방향이 반대면 `rpicam-hello` 에서 아무것도 안 나옵니다.

### 7-8. 배선 순서

**GND → 전원 → 신호** 순서로 하세요. 신호선을 먼저 꽂고 전원을 넣으면
래치업이 생길 수 있습니다.

전원 인가 전 멀티미터로 **5V–GND, 3.3V–GND 단락 여부**를 반드시 확인하세요.

## 8. 마커 팻말 설치

### 8-1. ID 배치

고랑 하나에 팻말이 **1개**입니다. **입구에만** 붙이고, 출구에는 없습니다.

| 위치 | 마커 ID |
|---|---|
| N번 고랑 **입구** | `N` |
| HOME (1번 고랑 입구) | `0` |
| **마지막 고랑 입구에 추가** | **`249` (END)** |

고랑 3개면: 입구 팻말 `1`, `2`, `3` / HOME 팻말에 `0` /
3번 고랑 입구 팻말에 `249` 추가. **출구에는 아무것도 붙이지 않습니다.**

입구 팻말 ID가 곧 **고랑 번호**입니다. 그래서 복귀 중에 팻말 하나만 봐도
"지금 몇 번 고랑 앞인지"를 바로 알 수 있습니다.

`DICT_4X4_250` 으로 인쇄하세요.

### 8-1-1. 팻말은 로봇이 지나는 길을 비켜서 박으세요 ★

고랑 중심선에 박으면 로봇이 진입하다 들이받습니다.

```
   ●  ← 팻말 (이랑 위, 중심선에서 0.30m 옆)
   ┊
   ┊ ← 로봇이 지나는 길 (고랑 중심)
```

**팻말 위치를 코드에 알려줄 필요가 없습니다.** 고랑이든 이랑이든,
왼쪽이든 오른쪽이든 로봇이 잘 볼 수 있는 곳에 세우면 됩니다.
중심선은 비전이 고랑을 보고 직접 찾습니다.
(`config.MARKER_POST_LATERAL_OFFSET_M` 은 시뮬레이터가 팻말을 배치할 때만
쓰이고 제어에는 관여하지 않습니다)

### 8-1-2. 그래도 너무 멀면 안 됩니다 — 횡오프셋 한계 ★

코드가 팻말 위치를 모른다는 것과, 얼마나 치우쳐 박아도 되는지는 다른
문제입니다. 너무 멀면 로봇이 팻말 앞에 도착했을 때 **정렬할 고랑이 센서
범위 밖**에 있습니다.

| 횡오프셋 | 비전 정상 | 비전 실명(흐린 날) |
|---|---|---|
| 0.20m | 완주 | 완주 |
| 0.31m | 완주 | 완주 |
| **0.33m** | 완주 | **SAFE_HALT (0/3)** |
| 0.60m | 완주 | SAFE_HALT |
| **0.65m** | **SAFE_HALT (2/3)** | SAFE_HALT |

- **약 0.32m — ToF 탐침의 한계 ≈ 고랑 폭.** 비전이 안 보이면 팻말 방위로
  다가간 뒤 코를 들이미는데, 팻말이 고랑 폭보다 더 옆이면 로봇 코가 이미
  이랑 위여서 좌우 벽을 못 잡습니다.
- **약 0.62m — 비전의 한계.** 이보다 멀면 고랑이 화면에 안 잡힙니다.

**권장은 0.15~0.20m** 입니다. 기본값 0.30m 은 첫 한계선 바로 밑이라 여유가
없어서, 팻말이 몇 cm 밀리면 맑은 날엔 멀쩡하고 흐린 날에만 SAFE_HALT 나는
고장이 됩니다. 위 숫자는 고랑 폭 30cm 가정이므로, 실제 폭을 잰 뒤 다시
뽑으세요 — 일반화하면 **"고랑 폭 이내, 여유 있게 그 절반쯤"** 입니다.

### 8-2. END 마커의 의미 ★

> "이 고랑이 마지막이다. **이 고랑까지 물을 준 뒤** 임무를 끝내라."

END 를 봤다고 그 자리에서 돌아서는 게 아닙니다. 평소처럼 진입 → 살수 →
유턴 → 복귀를 마친 **다음에** HOME 으로 향합니다.

END 마커가 없으면 로봇은 다음 고랑을 찾다가 상한에 걸려 `SAFE_HALT` 로
멈춥니다. "마커가 안 보인다"는 완료가 아니라 **모름**이기 때문입니다.
밭이 남았는데 마커가 흙에 가려진 것일 수도 있으니까요.

### 8-3. 팻말을 30도 기울여 박으세요 ★

팻말을 고랑에 **정면으로(수직으로)** 박으면, 로봇이 헤드랜드를 따라 옆으로
이동할 때 마커를 거의 옆면으로 보게 되어 검출되지 않습니다. 그러면 HOME
복귀 때 절대 기준점이 없어 엔코더 추측항법에 의존하게 되고, 바퀴가 한 번
미끄러지면 오차가 **누적**됩니다.

**전부 밭 끝(END) 쪽을 향해 30도 기울이세요.**

| 기울기 | 정면 접근 가능 거리 | 헤드랜드 검출 거리 |
|---|---|---|
| 0도 | 0.30 ~ 4.0m | 0.8m ← 복귀 때 안 보임 |
| 20도 | 0.30 ~ 4.0m | 3.6m |
| **30도** | **0.40 ~ 4.0m** | **15m+** ← 최적 |
| 45도 | 0.70 ~ 4.0m | 15m+ ← 정면 근접이 빠듯 |
| 50도 | 0.95 ~ 4.0m | 15m+ ← 실패 |

고랑을 빠져나온 로봇은 게이트 앞 **0.5~0.7m** 에 섭니다. 45도면 이 거리에서
마커가 시야각을 벗어납니다(시뮬레이션에서 HOME 을 못 찾고 밭 밖으로
나가는 것을 재현했습니다).

- **방향이 일정해야 합니다.** 반대로 기울이면 복귀할 때 뒷면만 보입니다.
- 30도로 보면 마커가 `cos30 = 0.87` 배로 납작해 보입니다. 검출 거리가
  15% 줄므로 `MARKER_SIZE_M` 을 **0.15 이상**으로 키우세요.
- 평평한 판에 붙이세요. **휘면 자세 추정이 망가집니다.**
- 모든 팻말의 **높이를 서로 맞추고**, 카메라 높이와 비슷하게 세우세요.
  (복귀 중 두 고랑의 팻말을 동시에 보고 헤드랜드 방향을 계산합니다)

## 9. 실제 동작 시 주의사항

### 9-1. 브링업 순서 — 건너뛰지 마세요

```
python3 selftest.py       # ① 150/150 나와야 함 (하드웨어 불필요)
python3 tools/setup.py    # ② 1→2→3 순서로
python3 main.py           # ③ 실제 임무
```

`tools/setup.py` 메뉴:
1. **센서 배선 점검** — 모터가 돌지 않습니다
2. **모터·부호 점검** — **바퀴가 실제로 돕니다. 받침대에 올려 띄우세요**
3. **흙 색상 보정** — 맑을 때와 흐릴 때 각각 맞추세요

### 9-2. 반드시 실측해야 하는 값

이것들을 기본값으로 두면 **로봇은 반드시 실패합니다.**

| 값 | 측정 방법 |
|---|---|
| `WHEEL_BASE_M` | 좌우 바퀴 접지면 중심 간 거리 (**각도 오차에 직결**) |
| `WHEEL_RADIUS_M` | 바퀴 지름 ÷ 2 |
| `TICKS_PER_REVOLUTION` | 바퀴 정확히 10바퀴 돌려 `총 틱 ÷ 10` |
| `MOTOR_MIN_DUTY` | setup.py 2번에서 실측 |
| `MARKER_SIZE_M` | 인쇄된 마커 한 변을 자로 |
| `HEADLAND_STEP_DISTANCE_M` | 고랑 중심 간 실제 간격 |
| `CAMERA_MATRIX` / `DIST_COEFFS` | 체스보드 20장 → `cv2.calibrateCamera` |

**카메라 캘리브레이션을 건너뛰면 입구 정렬이 계속 실패합니다.** 지금은
"초점거리 ≈ 이미지 폭"이라는 거친 근사값을 쓰고 경고를 띄웁니다.

### 9-3. 첫 주행

`BASE_SPEED = 0.2`, `LOG_LEVEL = "DEBUG"` 로 두고 이 순서로 넓혀 가세요.

1. 물 없이 빈 고랑 1개 왕복
2. 물 넣고 고랑 1개
3. 고랑 2개 (헤드랜드 이동 포함)
4. 전체 밭

**각 단계마다 비상 전원 차단 스위치에 손을 올려두세요.**

### 9-3-1. 무한궤도(트랙) 사용 시 ★

궤도는 바퀴와 물리가 다릅니다. 두 가지만 이해하면 됩니다.

**(1) 회전할 때 궤도가 지면을 비비며 미끄러집니다 (skid steer)**

바퀴는 굴러서 돌지만 궤도는 좌우가 반대로 밀면서 지면을 긁습니다.
그래서 같은 좌우 속도차를 줘도 **이론값보다 덜 돕니다.**

```
TRACK_WIDTH_M = 0.17        ← 자로 잰 실제 궤도 간격
TRACK_SLIP_FACTOR = 1.3     ← 미끄러짐 보정 (실측)
WHEEL_BASE_M = 0.17 × 1.3 = 0.221   ← 코드가 회전 계산에 쓰는 값
```

**`TRACK_SLIP_FACTOR` 가 궤도에서 가장 중요한 값입니다.** 이게 틀리면
유턴과 헤드랜드 선회가 전부 어긋나 밭 밖으로 나갑니다.

**(2) 엔코더는 '궤도가 움직인 양'을 잽니다**

로봇이 실제로 간 거리가 아닙니다. 궤도가 흙에서 헛돌면 엔코더는 더
갔다고 보고합니다.

```
DISTANCE_CALIBRATION_FACTOR = 실제 이동거리 ÷ 엔코더 추정거리
```

딱딱한 바닥이면 1.0 에 가깝고, 무른 흙이면 0.9 근처까지 떨어집니다.

**두 오차 모두 흙 상태에 따라 달라져 계산으로 못 구합니다. 재는 수밖에
없습니다.**

```bash
python3 tools/setup.py 4     # 궤도 보정 (바닥에 내려놓고)
```

로봇을 2m 직진시키고 180도 회전시킨 뒤, 실제 값을 자로 재서 입력하면
config 에 붙여넣을 세 줄을 출력해 줍니다.
**실제 밭 흙 위에서 재야 의미가 있습니다.**

**그 밖에 궤도에서 달라지는 것**

- `MOTOR_MIN_DUTY` 가 바퀴형보다 높습니다(보통 **0.25~0.40**). 궤도는
  정지마찰이 크기 때문입니다. 낮게 두면 미세 조향 명령이 무시되어
  정렬이 영원히 수렴하지 않습니다.
- 제자리 회전은 궤도가 오히려 **유리**합니다. 횡변위 없이 피벗하므로
  입구 정렬 3단계(진입각 조정)가 깔끔하게 됩니다.
- 엔코더 각도가 부정확하므로 **비전과 ToF 의 역할이 더 큽니다.**
  ToF 탐침이 각도 대신 좌우 거리차만 쓰는 것도 이 때문입니다.

### 9-4. 바퀴 미끄러짐 한계

시뮬레이션으로 검증한 범위는 **좌우 대칭 미끄러짐 2% 이내**입니다.
(마커가 입구에만 있는 배치 기준. 고랑 안에서는 마커로 위치를 보정할
기회가 아예 없으므로, 회전 오차를 바로잡는 지점이 고랑 입구뿐입니다) 그 너머에서는 폭주하지 않고 `SAFE_HALT` 로 멈추지만 임무를 마치지
못합니다.

무른 흙이나 비 온 뒤라면 **IMU(자이로) 추가**가 근본 해결입니다. 회전
각도를 엔코더가 아니라 자이로로 재면 미끄러짐과 무관해집니다. MPU-6050
급이면 1만원 이하고, I2C 버스에 ToF 와 같이 물리면 배선 3선만 추가하면
됩니다.

### 9-5. SAFE_HALT 는 고장이 아닙니다

로봇이 **"확실한 근거 없이는 진행하지 않는다"** 는 원칙으로 설계되어
있습니다. 애매하면 멈추고 사람을 기다립니다.

`main.py` 는 결과를 종료 코드로 알립니다.

| 코드 | 의미 | systemd 동작 |
|---|---|---|
| 0 | 임무 정상 완료 | 재시작 안 함 |
| 2 | `SAFE_HALT` (사람 확인 필요) | **재시작 안 함** |
| 1 | 예기치 못한 오류 | 10초 후 재시작 (최대 3회) |

`Restart=always` 로 두면 안 됩니다. SAFE_HALT 는 "스스로 판단하기를 포기하고
사람을 기다리는 상태"이며, 자동 재시작은 같은 사고를 무한 반복합니다.

### 9-6. 알려진 한계 — 알고 쓰세요

1. **장애물 감지가 전혀 없습니다.** 사람·동물·돌이 앞에 있어도 모르고
   그대로 갑니다. 전방 ToF 나 범퍼 스위치 추가를 강력히 권합니다.
   **첫 주행에는 반드시 사람이 따라다니세요.**
2. **단일 채널 엔코더** — 회전 방향을 모터 명령으로 추정합니다.
   정밀도가 필요하면 쿼드러처(A/B) 엔코더로 교체하세요.
3. **비전이 색상 임계값 기반** — 그늘·역광에 약합니다.
4. **밭 밖으로 나가는 것을 막는 물리 장치가 없습니다.** 소프트웨어
   상한뿐입니다.

### 9-7. 자주 겪는 문제

| 증상 | 원인 |
|---|---|
| `ModuleNotFoundError: sensors` | 프로젝트 루트에서 실행했는지 |
| `ModuleNotFoundError: picamera2` | venv 를 `--system-site-packages` 로 만들었는지 |
| ToF 초기화 실패 | `i2cdetect -y 1` 로 0x30/0x31, XSHUT 배선 |
| 고랑 진입 3초 후 SAFE_HALT | ToF 가 벽을 못 봄. 장착 각도/높이 |
| 입구에서 15초 후 SAFE_HALT | 카메라 캘리브레이션, `MOTOR_MIN_DUTY` |
| "비전 신뢰도 부족" 반복 | `tools/setup.py` 3번으로 HSV 재튜닝 |
| **오차를 키우며 벽으로 감** | **부호 문제.** setup.py 2번 후 `SIGN_*` 뒤집기 |
| 제어 루프 주기 초과 경고 | `CAMERA_RESOLUTION` 낮추기 |
| Pi 가 갑자기 리부팅 | 모터 전원을 Pi 에서 뽑고 있음 |
| 프로그램 켜자마자 물이 쏟아짐 | MOSFET 게이트 풀다운 없음 |

## 10. 자체 점검이 검증하는 것과 못 하는 것

`selftest.py` 150개 항목은 **상태 전이, 부호 규약, 워치독, 인터록,
고랑 끝 판정, 미끄러짐 내성**을 검증합니다.

하지만 **바퀴 미끄러짐의 실제 크기, 조명 변화, 모터 응답 지연, 흙의 실제
색상**은 검증하지 못합니다.

> **"여기서 통과 = 실기에서 잘 달린다"가 아니라,**
> **"여기서 실패 = 실기에서는 확실히 실패한다"** 로 읽으세요.
